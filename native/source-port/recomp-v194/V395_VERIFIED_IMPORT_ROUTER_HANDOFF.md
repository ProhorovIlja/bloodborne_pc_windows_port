## Critical safety, provenance and user goal

1. This only exercises SEVEN invented x86 functions and THREE synthetic example import modes. **No real original Bloodborne 1.09 function or original PS4 API import ABI and actual game service target graph is proven to work**. Only owner-private original game files should be inspected for complete function hashes, generated AOT paths, real import manifest and correct input/output ABI. Their retail game bytes, decrypted code, DS3 files, credentials and private assets MUST NEVER be posted to public GitHub/CI.
2. V395 route is immutable after seal only by a contract that the caller serializes registration and never modifies its memory externally. Source code is still C, not protected against arbitrary malicious host memory corruption. Process-global callable import callback must retain the router and owner memory for the lifetime of every native worker.
3. Recovery is cooperative V393 same-thread only. It is NOT OS fault/SEH, C++ exceptions, pthread cancellation, signals, raw `longjmp`, abort or cleanup across foreign resource owners. Skipped frames with live handles/locks would be unsafe. V390 leases must bracket ALL real original-generated functions, direct native calls, callbacks, GPU workers and host imports before V389 dynamic remap can be trusted.
4. Genuine upstream generator supports guest-runtime interpreter fallbacks for incomplete instructions; in our synthetic tests `RcApi.step/tail/bail` abort and no translator executes, but original full game closure is UNPROVEN. The actual original AOT corpus includes many more functions and legal licensed libraries. Existing public `bloodborne-native/bloodborne-recomp` mainline documents that it retains translator fallbacks and the game still depends on PS4 HLE/runtime. Its source is useful but is **not** equivalent to the user's strict independent no-EBOOT/no-PS4-runtime goal.
5. Native V390/V391/V395 cross-word/unaligned SIMD and x86 LOCK atomic, guest memory aliases, guest page/CPU faults and thread ordering are incomplete. Two 64-bit reads for sum are not a consistent multithread transaction. The compiler object symbol/relocation audit cannot prove a whole original-game image contains no raw guest pointers.
6. The user goal remains a fully independently booting original Bloodborne 1.09 Windows x64 PE32+ and Linux x64 ELF64 game (later Apple Silicon ARM64 native) without runtime PS4 `eboot.bin`/SELF/ELF/interpreter/translator/emulator, complete playable gameplay/DLC/chalices/save/native renderer/D3D12/Vulkan/shaders/streaming, frame pacing and optimization, controller/KBM/chords/HUD/dedicated jump/NG+, stable low-latency online/LAN/client/server/launcher and legally supported optional DLSS/FSR/XeSS/Reflex/HDR. **V395 does not boot the original game.** The separate playable BBPort/BBSC Yharnam Together Ultimate stream must be preserved.
