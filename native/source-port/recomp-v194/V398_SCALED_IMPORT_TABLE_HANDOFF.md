# Native V398 — scalable sealed host-import registry without changing actual generated guest memory semantics

2026-11-12. Independent native Bloodborne PC source-port branch `feature/native-v398-scalable-sealed-imports-20261112`, based on V397 Draft PR #127 and V396 #126, separate from the playable BBPort and BBSC Ultimate Yharnam Together client/launcher/server/network project. **This is NOT a runnable original Bloodborne game.**

## Engineering issue addressed

V397 added exact (target, next RIP) authorization for multiple callers of one host native import, but stored at most **16 sites** in a fixed structure holding 16 copies of V395's 16-site router. This is wasteful and inadequate to stage any substantially larger owner-private original-game import graph. The V397 per-target linear scan for next RIP was also unbounded relative to target fan-out (up to 16 in the test), so it should not simply be raised to thousands without a bounded, indexed data structure.

## Actual V398 source work

- `native_scaled_import_v398.h/.c`: dedicated sealed controller-owned heap array of `ShytNativeImportSpecV395` with **maximum 8192 entries** and a caller-selected fixed capacity. The array is allocated exactly ONCE during single-thread setup, with no `malloc/realloc/free` in any generated `RcApi.call` hot path. All entries are validated using the original V395 service whitelist (three synthetic services only), and duplicate exact (target,next) or reused targets with conflicting service/ABI/recovery code/constant are refused before sealing. `qsort` sorts all entries by guest target and generated native source continuation; sealing verifies strict order and ABI consistency. During execution, two lower-bound binary searches locate first the target and then its precise allowed return RIP, in **O(log N)** comparisons; unknown targets recover via V393 reason **501**, wrong return next with a known target reason **502**, with NO guest output mutation or translator fallback. Exact matches dispatch to the original V395 service under existing V390 same-owner lease, V393 trusted cooperative recovery and V388/V389 logical OS-backed guest VM/permissions.
- `native_verified_import_v395.h/.c`: the original V395 fixed-service body was factored into `shyt_native_import_spec_valid_v398` and `shyt_native_import_dispatch_site_v398` (validates the active VM owner lease, V393 checkpoint, exact target and exact next RIP, guest data permissions and original three synthetic service semantics). The legacy V395 sealed router keeps its original public `shyt_native_import_dispatch_v395` symbol and delegates to the identical shared body, avoiding duplicated or diverging permission checks. V397's old implementation remains unchanged and is tested by inherited workflows.
- `shyt_native_scaled_release_v398` is a controller-only shutdown operation. It does NOT free a live native table: it requires the V386 owner VM to be **irreversibly closed and quiescent**, plus explicit positive confirmation that ALL possible original generated/host callback threads have been JOINED. This gate prevents normal misuse; the caller must actually enforce thread lifetime and quiescent truth. Release zeroes router structure's pointers/count/capacity but cannot stop a malicious controller from lying about a join.
- `test_native_scaled_import_v398.c`: inherits V397's seven **genuine upstream bbrecomp-generated whole-function C** from wholly invented x86-64 LOCK CMPXCHG, SSE128 MOVDQU, AVX256 VMOVDQU and two independently emitted CALL RAX guest functions. Both real generated CALL RAX sites use the SAME source-attested target at **0x40009100** with separately authorized continuation RIPs **0x4010a2** and **0x4010c2** from the V397 SHA-256-pinned independent invented ELF manifest. The tests cover RAX/guest return correctness, exact guest atomic qword read/write and denied RO/unmapped stores, unknown/wrong-next recovery without memory mutation, conflicting ABI and duplicate registration rejection, cooperative nested callback recovery, OS VM page remap and active-lease PAUSE refusal. The original cross-word locked memory/invalid guest access negative POSIX cases stay fail-closed.
- The test additionally performs a **separate, HOST-ONLY stress** with 1024 unique route targets + 16 distinct continuations for one additional shared target (1040 total) on a second native test VM owner. These 1040 fabricated stress entries are NOT part of the seven generated x86 function bodies and are NEVER published to their `RcApi.call` callback route, so they must not be mislabeled as source-attested original-game imports. It verifies capacity, reversed insertion, sorted first/last indexes, strict duplicate/incompatible rejection, seal immutability, refusal to release while VM open, and release only after close/quiescence/thread join. The synthetic proof is scalable registration and sorting, **not** an 8192-call benchmark.
- `.github/workflows/native-v398-scalable-import-table.yml`: independently builds the exact pinned public `bloodborne-native/bloodborne-recomp` compiler revision `8f31ec7c41f252730c6325d52647046baef7549f`, emits the same invented ELF build-time-only and actual generated C source, uses V390 strict VM instrumentation, V392 whole-shard source audit, V395 compiled ELF symbol/relocation gate, V396 SHA256 source function/callsite manifest, V397 shared-target exact-source negative tests, compiles real generated C plus scalable native host table on Linux GCC/Clang and Clang AddressSanitizer+UBSan. Windows AMD64 native PE32+ clang-cl strict /W4 /WX host code, and Apple ARM64 macOS host-only tests run when available. The inherited V397/V396/V239 workflows should still pass without semantic regression. No actual retail Bloodborne/DS3 binaries, EBOOT/PS4 firmware, private generated commercial source or keys are published to GitHub Actions.

## Safety, architectural and correctness bounds

- The table **max=8192** is a staging capacity, NOT a complete original Bloodborne 1.09 import graph. Actual original-game import coverage and typed ABI/prototypes/return-source attestations have NOT been measured, and indirect CALL RAX targets can be dynamic. No real original-game code, data or resources have been executed.
- Performance improvement is structural: constant storage per site and binary search rather than V397's per-site 16-router copies/target linear scan; **no game FPS, CPU budget or import dispatch microbenchmark** is claimed. Pre-seal O(N) conflict checks per registration and `qsort` are outside the native hot path.
- V395's demo services remain return-constant, qword sum to guest output and explicit cooperative failure, **not real Bloodborne system imports**. Guest qword read/write C11/OS VM memory model, cross-word LOCK/CAS, actual page traps, SIMD store atomicity, x86 and ABI parity remain incomplete.
- V393 recovery is strictly **cooperative, synchronous, same-thread trusted host callback**. It cannot safely handle arbitrary raw `longjmp`, POSIX signals, SIGSEGV, Windows SEH, C++ exceptions, cancellation, hard abort or skipped frames with foreign resources; such execution may strand a lease. V398 heap lifetime needs all actual guest AOT workers and callbacks joined before free.
- No genuine original Bloodborne 1.09 independent native Windows PE32+/Linux ELF64 game startup without PS4 EBOOT/SELF/runtime/interpreter/emulator, original AOT closure or import graph, native renderer Vulkan/D3D12/Metal, graphics/shaders/streaming, physics/AI/DLC/chalices/saves, PC keyboard/mouse+controller/NG+/HUD/QoL, online LAN/P2P/dedicated server/client/launcher, stability/optimization/frame pacing or measured latency proved. Apple ARM64 synthetic host compilation is not a native Apple Silicon original-game port.
- Original legally owned game source/assets/DS3 files and owner-specific private Drive data must remain private, never uploaded to public GitHub/CI. This source-only branch does not provide or copy game data.
- Public GitHub PR/fork/branch provenance remains important, but this checkpoint targets a concrete audited native dispatch bottleneck rather than an unsupported claim of globally searching all GitHub/internet/Drive.
