## Problem and implemented contract

V396 checked that all source-emitted `RcApi.call` sites in the **seven invented** x86-64 functions were declared in an independently SHA-256-pinned manifest, and generated a C array `shyt_v396_sites[]`. V398 built a scalable O(log N), max-8192 sealed import route but its main synthetic demonstration also registered several extra hand-authored demo imports. There was no separate native bootstrap that could refuse a truncated attested array and verify actual compiled `RcFunction` function entry offsets/sizes before authorizing every real generated host call.

V399 adds `native_attested_import_v399.h/.c` with `shyt_native_bind_attested_v399`. It accepts (1) actual generated `RcFunction` offset/size/nonzero numeric hash/native function/direct-slot metadata, (2) **all** entries from the build-time SHA256/source-locked V396 `shyt_v396_sites[]` C header, (3) independently attested expected site count and (4) exact guest image base. All validation happens BEFORE allocating the sealed table. Each source caller must exactly match a compiled entry in the sorted, nonoverlapping function registry. Each generated `expected_next` guest RIP must be strictly inside its owning function's code interval (not the first byte, not at/after the end), with checked integer bounds. Duplicate source/return pairs, reused guest target with different fixed service ABI/recovery/constant, duplicate target+return, noncompiled/zero-hash/missing direct slot metadata, untrusted image base, missing/extra source callers or truncated site count fail closed.

The genuine pinned upstream `bloodborne-native/bloodborne-recomp` `RcFunction.hash` has **uint64_t**, not `const char*`; V399 verifies a nonzero 64-bit hash and does not treat this scalar as a string/pointer. Source revision pinned `8f31ec7c41f252730c6325d52647046baef7549f`. The build-time V396 source/Python verifier, not the V399 runtime bootstrap, is responsible for SHA256 of the invented input ELF, source instrumented C and complete enumerated guest callsites. The V399 bridge checks structurally that every attested entry it is given corresponds to a compiled function; it cannot independently recalculate AOT compiler hashes or infer dynamic indirect call targets.

On successful complete preflight, the bridge allocates exactly `site_count` V398 entries, inserts only the validated guest-target+return-site pairs, then sorts and seals the router for read-only lookup. Any unexpected insertion/seal error during single-thread construction rolls back this private unpublished allocation. It does NOT add legacy test-only constant or failure services to this new attested router. Normal V398 dispatch still requires active same-owner V390 guest VM lease, a live V393 trusted cooperative recovery frame, exact guest target and return RIP, V395 permission-checked memory I/O, and no guest interpreter fallback. The table is destroyed only after VM close, quiescence and all potential access threads joined.

## Honest limitations

Only **seven invented x86-64 machine-code functions** are compiled through the pinned public generator. No original Bloodborne 1.09 source/game code or full owner-private original function graph, import prototypes, API ABIs, SHA256 or full runtime indirect target closure have been verified. The V399 numeric hash existence check is NOT independent hash equality validation. The V396 build-time SHA256/source manifest assertion is separately verified in CI, not recalculated at runtime. No original standalone Windows PE32+ / Linux ELF64 Bloodborne executable or independent native game boot without PS4 EBOOT/SELF/guest interpreter exists as a result of V399.

V393 explicitly cooperative same-thread trusted callback recovery is NOT general fault/SEH/signal/C++ exception/cancellation/host crash safety. x86 cross-word LOCK atomic, guest page/fault and SIMD atomicity semantics are incomplete. Native renderer D3D12/Vulkan/Metal, shader streaming, actual game assets/AI/physics/campaign/DLC/chalices/saves, keyboard/mouse/controller chords/HUD/manual NG+, robust low-latency online/P2P/LAN/dedicated server/client/launcher and measurable FPS/frame pacing remain separate large development milestones. Apple ARM64 host synthetic CI does not establish original ARM64 game port.

If user-owned Bloodborne/DS3 materials are used later, all originals, generated copyrighted retail game code and private layout/hashes must stay owner-only, never on public GitHub, public CI, or shared handoff documents.
