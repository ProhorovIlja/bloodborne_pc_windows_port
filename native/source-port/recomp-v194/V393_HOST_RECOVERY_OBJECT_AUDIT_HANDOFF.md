## Evidence-backed implementation

1. `native_host_recovery_v393.{h,c}`: `shyt_generated_call_recoverable_v393` uses a C11 `setjmp` checkpoint in the caller-owned synchronous generated RcFn entry wrapper, with one `_Thread_local` bounded (max 16) stack of checkpoint frames per thread. Invokes the existing V392 scoped native function call with a real V390 / V386 OS-backed VM lease; nested **same-owner** V392 scopes borrow the existing pin. If a trusted same-thread preflight or explicit host callback calls `shyt_generated_raise_v393(code)`, C `longjmp` returns to the wrapper's own still-live checkpoint. V393 pops its TLS frame, releases its V392 scope (or leaves borrowed owner pin for outer checkpoint), and returns `SHYT_V393_RECOVERED` plus a positive reason code. Controlled normal C return is `SHYT_V393_COMPLETED` and preflight-denied path is `SHYT_V393_DENIED`; both leave no newly owned lease outstanding. The reported reason and wrapper status use volatile locals as required by C11 setjmp semantics.

2. Scope ownership invariants are inherited intact from V392: a nested generated function cannot borrow another VM owner; V389 `PAUSE` is denied while an active owned/borrowed lease exists. The new API does NOT introduce an independent guest translator or a raw pointer to game guest memory.

Finally actual compiler-generated LOCK/CAS function runs through the V393 normal-return wrapper. All retail Bloodborne and DS3 game bytes remain absent.

## Strict limitations — no false exception safety

V393 is safe only for deliberate **cooperative** `shyt_generated_raise_v393` in a synchronous TRUSTED host callback, with no skipped frames that own locks, memory, open resource handles or C++ nontrivial destructors. It does **NOT** intercept a raw arbitrary C `longjmp`, POSIX signal, `SIGSEGV`, `SIGABRT`, Windows SEH, C++ exception, cancellation, or hard host crash. Those flows can still skip V390 lease cleanup, strand VM pins or corrupt state. These are game-port production blockers until an explicit and tested platform-native exception/unwind design is provided.

Native object symbol/relocation checks show important VM helper dependencies and absent known guest runtime symbols in this **specific generated synthetic object**. They do **NOT** prove no guest-pointer raw memory dereferences were inlined or generated in other functions. They are not full compiler AST/LLVM IR or disassembly proofs for the entire original game. Original Bloodborne 1.09 owner-private full generated AOT corpus, all guest memory code paths, x86 atomic cross-word/page semantics, aliasing, thread service callbacks and original import graph are still missing.

Cross-word CAS remains deliberately unsupported and causes abort; 16/32-byte SIMD stores span multiple atomic buckets and are not indivisible memory transactions. OS remap is valid only while ALL paths hold V386 leases. Game program code cannot safely assume this across async callbacks or host exceptions.

**No original Bloodborne game independent native Windows PE32+/Linux ELF64/Mach-O executable has been verified.** The five invented functions are not original retail game code; this is not a playable native game. D3D12/Vulkan renderer/asset streaming, shaders/VRAM/AI/physics/animation, DLC/chalices/saves, PC keyboard/mouse+controllers/chords/jump/HUD/NG+, multiplayer online/LAN/client/server/launcher, native clocks, measured frame pacing and CPU/GPU performance all remain substantial independent work. Apple Silicon host-native synthetic C does not constitute game ARM64 compilation. All owner game files stay in private storage.
