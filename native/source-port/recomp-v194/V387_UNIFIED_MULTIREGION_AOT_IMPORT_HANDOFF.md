## Source-level integration
- `native_boot_chain_v384.h/.c` exposes a V387 stack-writer-selectable STRICT AOT finalizer, retaining `shyt_native_boot_finalize_v384` as a backwards-compatible wrapper. The same original upstream RcApi v4 with real V245 math/clock AOT registration and exact supplied-function attestation is used. This chooses V386's `shyt_native_vm_stack_write_v386` BEFORE the irreversible V382 function dispatch snapshot is published. No post-publication mutation of native AOT memory callback.
- `native_unified_import_v387.h/.c` adds `shyt_native_boot_finalize_multiregion_v387`: requires V386 immutable sealed mapping and validates an exact R+W V386 region matches the V383 sidecar preflight stack base, host backing, word count. The V383 sidecar is for V384 bootstrap preflight only. Actual native AOT CALL/TAIL uses the V386 mapped stack, and its original `BbCpu` register contract.
- V387 final import preparation verifies complete supplied table admission, owner attestation, V386 writer exact identity, V245/V384 published routes, 23 distinct original math names/offsets/native handler identities, two distinct Windows QPC clock import targets, no compatibility raw-pointer fallback.
- Once-only `RcApi.call` publication routes all 23 known math plus 2 Windows clock imports using V386 atomic guest memory/leases; unknown targets go directly to verified V382 native function resolver and ABORT if missing. `step` and `bail` remain V381 interpreter tripwires.
- `frexp`/`frexpf` 4-byte exponent outputs can be in separate writable V386 region while return address is in stack region. Preflight ensures both addresses are mapped, write-authorized, within a single 8-byte atomic word, disjoint and overflow-free. Read-only, unmapped, return-overlapping, crossing-word and closed mapping outputs reject and leave CPU+guest bytes intact. A W-only region supports output but not reading through guest VM.
- V386 guest memory lifecycle: pin for the entire math/clock native import through computed guest writes, close denies NEW pins while existing pinned operations finish. All owner threads must JOIN before backing/state is freed. VM mapping immutable and W^X, not a true OS VM manager.

`test_native_unified_import_v387.c` builds and executes real pinned V245 / V384 generated-code callback registration in native Windows PE32+ (SYNTHETIC two RcFns, NOT game), with 4 V386 guest regions (R+W stack, R+W exponent/output, R-only, W-only), all 23 math import signatures and 2 clocks, native-only AOT CALL+TAIL, unknown target diagnostic, denied invalid output pointers, W-only exponent output, denied imports after close and zero calls through V226/V239 raw host-pointer importer callbacks. ## Crucial remaining boundaries
- V387 shares one immutable V386 address-space backing for 25 known imports and a supplied AOT function table, but the original Bloodborne game's genuine entire 1.09 code and thousands of imports/symbols have NOT been supplied, attested, linked or run. The upstream generated AOT code's actual memory operations may not use these VM functions. This is NOT a full replacement for PS4 runtime/translator or working game boot.
- V386 supports only one-atomic-word 1/2/4/8 byte operations. Original game requires multi-word/cross-page, unaligned accesses, actual Windows/Linux/macOS OS page protections, paging/mapping/unmapping and multithreaded lease invalidation, host imports beyond math/clock, native GPU/audio/input/physics/saves/online.
- Legacy V226/V239 direct-host-pointer adapters still compile for V245 bootstrap but the V387 final RcApi published callback does not delegate recognized imports to them. Future work should retire/replace legacy raw import code and prove no route bypass.
- The Windows QPC host clock is not Linux-native yet; Linux & macOS ARM64 CI are C11 host regression only. Apple Silicon compiling one host unit is not an ARM64 Bloodborne game.
