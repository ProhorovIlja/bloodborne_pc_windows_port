# V464: startup virtual-call route

Private read-only check on the CUSA03173 ELF from Drive: both calls in constructor 1074 use vtable offset 0x20. On the statically identified cold path, the singleton factory initializes a subobject at offset 0x458 before publishing the singleton. The associated vtable slot has an executable-relative relocation to a complete leaf: one four-byte store to caller-owned return storage and a return of that storage pointer. This is the dependency object's method, not one of the two getters on the object that 1074 publishes. The pre-existing singleton path still requires observation after constructors 1–1073. Additional virtual calls within the factory and mutex path are not covered.

The route helper matches the callsite, guest receiver, current vtable and current target before issuing the bounded 32-bit guest write. It never calls the guest target. The return-register output changes only on success. The caller must establish writable guest return storage through its memory adapter, provide independently verified route data and stop on rejection. The helper is not yet connected to the ordered retail harness. No new constructor returns, gameplay or retail Windows/macOS execution is claimed.

External comparison: DDisasm/GTIRB is a secondary offline CFG tool; SCE metadata must be normalized before using generic ELF tooling. XenonRecomp demonstrates a fast address-to-host-function table, but lookup by target alone does not validate the receiver or vtable. bloodborne-recomp remains useful for independent scan and differential replay, not as an unmodified no-fallback runtime. No upstream code, game bytes or absolute retail addresses are included.
