Date: 2026-11-12. Native Bloodborne independent PC source-port branch `feature/native-v400-independent-function-identity-20261112`, based on Native V399 draft PR #129, V398 #128 and preceding V397–V386 branches. ## Problem resolved for the synthetic source-port experiment

V399's runtime import binding verified that each generated `CALL RAX` site belonged to a sorted compiled function registry, and required only a **nonzero** 64-bit `RcFunction.hash`. A malicious or stale generated function registry could change its source code while keeping a nonzero hash, pass that existence check and publish a wrong-function host import route. V400 adds independent input-byte and function-hash equality checking at BOTH build time and native router bootstrapping.

The actual pinned public upstream `bloodborne-native/bloodborne-recomp` revision `8f31ec7c41f252730c6325d52647046baef7549f` writes each generated `RcFunction` row with offset, size and the result of `bbcpu_recomp_hash(base+offset,size)`. The public sibling source `bloodborne-native/bbcpu/src/cpu/recomp.c` defines `bbcpu_recomp_hash`: 64-bit FNV-1a with offset basis `0xcbf29ce484222325` and multiplier `0x100000001b3`, mixing each decoded instruction's x86 bytes. **Exception:** recognized FS/GS thread control block loads are normalized by an alternate instruction+register hash. V400 explicitly restricts itself to the **seven invented x86 functions** that have no special TCB instruction; it does **not** claim this simple byte algorithm is correct for the full original Bloodborne image. A separate owner-private decoded instruction hash verifier will be required for the real game.

## Explicit limits — no native game completion claim

1. The independent hash implementation is only proven for **seven invented x86-64 functions** containing no recognized special TCB FS/GS loads. Upstream hashes **decoded instructions**, not simply arbitrary contiguous raw original-game bytes. Original 1.09 game code has dynamic patches, mapped ELF segments and TLS/TCB special normalization; the exact real private function identity checker must implement all these cases and owner-safe address translation, possibly with decoder provenance. A pass of this tiny fixture does NOT establish complete game AOT source/function equivalence.
2. This stage verifies a source image and generated C table at **compile time** and independently checked numeric identity before the runtime sealed route. It does NOT validate every possible real game native import ABI/prototype or dynamic indirect target; the actual game has many more caller sites than the two test CALL RAX sites.
3. V393 `setjmp` recovery is ONLY explicitly trusted same-thread cooperative callback, NOT arbitrary raw `longjmp`, SIGSEGV/SEH, signals, C++ exceptions, cancellation or hard crash. V390/V389 pin lifetime under real game worker threads/faults is not yet proven. Cross-word LOCK atomic, precise SIMD fault semantics and guest host memory aliasing remain incomplete.
4. No original Bloodborne 1.09 independently booting native Windows PE32+/Linux x86_64 ELF64 (later macOS ARM64 Mach-O) game with no runtime PS4 `eboot.bin`/SELF/interpreter/translator/emulator; no validated original game native renderer D3D12/Vulkan/Metal, shader/asset streaming, game physics/AI/animation/campaign/DLC/chalices/saves, PC KBM/controller/chords/jump/HUD/manual NG+, online LAN/P2P/server/client/launcher or measured FPS/frame pacing/network latency exists on the basis of V400.
5. The original owner Bloodborne game/DS3 files, private generated retail C, textures, source hashes and credentials remain private and are NEVER uploaded into this public GitHub/CI/Drive project. The public Github source research and pinned bbcpu algorithm are distinct from access to owner-only original-game code. Preserve the separate playable BBPort/BBSC Ultimate Yharnam Together stream.
