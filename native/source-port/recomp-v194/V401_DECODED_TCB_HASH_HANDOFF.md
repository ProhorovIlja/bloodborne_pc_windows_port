## Proven upstream algorithm and why V400's simple code-byte FNV is not enough

V400 independently verified exact `RcFunction` offset/size/64-bit hash for the first **seven wholly invented** x86-64 functions without TLS/TCB loads, comparing original synthetic ELF machine bytes against the actual pinned public `bloodborne-native/bloodborne-recomp` compiler table. Generalizing that proof to arbitrary original Bloodborne 1.09 code by FNV-hashing all raw bytes would be incorrect. The pinned source `bloodborne-native/bloodborne-recomp`, commit `8f31ec7c41f252730c6325d52647046baef7549f`, `src/cpu/recomp.c` defines `bbcpu_is_tcb_load` and a `hash_more` loop. Decoder-qualified **MOV reg64, FS:[0]** or **MOV reg64, GS:[disp]** with absolute base and no index gets normalized to 0xF5 and the decoded destination GPR ID (then other instructions in the function are mixed normally). FS:[nonzero displacement] is not normalized; neither arbitrary MOV nor any unknown guest code may assume that exception. The public compiler `tools/recomp/bbrecomp.c` emits `r[dest] = c->tcb;` for the same decoded instruction category. Public pinned source blob SHA: `src/cpu/recomp.c` `2e005442aacaa835e5b3c2f3522d63b0c04bc8fd`, `src/cpu/decode.c` `e3a84f800ae70f78ccaea6ea7c456ebd97d502fc`. The function table compiler blob remains pinned by V395 `f5032c9ead4988579e005af8a0a0ce4ba4ab66d8`. This is source-backed engineering, not actual Bloodborne original-code parity.
