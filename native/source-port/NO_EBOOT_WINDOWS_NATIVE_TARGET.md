# Bloodborne Native Windows: non-negotiable target and source-first work

**Goal:** a complete, genuinely native Windows 10/11 x64 game, analogous in *runtime architecture* to the official PC release of Dark Souls III. It must launch from our own `Bloodborne.exe` without reading, mapping, decoding, interpreting or loading `eboot.bin` or PS4 ELF at runtime. A Windows launcher and native server are part of the eventual product, **but gameplay must work completely offline first**.

## Definition of done (NOT achieved)

1. **Real standalone Win64 build:** compiled game logic, own Win32 process entry and native Windows host libraries. No guest-CPU interpreter/JIT, Orbis syscall dispatcher, PS4 kernel process or emulator-based runtime. Any original PS4 code, if recompiled from a user's legally obtained title, is source input at **offline build/installation time only**, not an executable payload at runtime.
2. **Whole-game engine execution:** all necessary gameplay functions, call graphs, exception handling, memory/threads/TLS, file and world streaming, physics, events, animation, NPCs and AI, save/load including corrupted-save safety, all bosses, all endings, NG+, chalices and The Old Hunters. A count of recompiled functions is not an end-to-end game test.
3. **PC subsystems:** true native DirectX 12 or Vulkan rendering from engine-level data (not PS4 GNM command-stream execution forever), keyboard/mouse/gamepad, native windowing and display timing, high-refresh rendering without game-speed bugs, native audio/movie backends, configuration and mod loading. Reuse original user-owned Bloodborne resources or *offline*-converted PC resource formats, not third-party bundled game assets.
4. **Only then**: optional online engine, P2P where possible with authenticated server control and secure fallback, native matchmaking/invasions, five total seats, co-op, QoL, native launcher/update/install, native dedicated server, telemetry opt-in and a polished distribution experience. All multiplayer behavior must be tested inside the real native game.
5. **Proof:** repeatable offline Windows game launch without `eboot.bin`; playthrough + Old Hunters + chalices; real hardware compatibility and perf/memory metrics; no game-derived public artifacts. The result must survive a clean Windows 11 install where PS4 runtime/emulator libraries are absent.

## What our present code ACTUALLY proves

- Drafts #77-#84 contain native asset parsers, actual LLVM Win64 COFF/PE toolchain feasibility, and private 1.09 game-code samples. V193 classified **9,955** strict 16-byte FDE intervals into **10 narrowly supported grammars**, compiled these into native Windows COFF/DLL privately, and ran differential checks under tightly limited circumstances. This is not all of Bloodborne, an executable engine or Windows gameplay.
- **Native V194** `recomp-v194/full_cpu_abi_v194.h`: checks **ALL** fields of upstream `BbCpu` against `bloodborne-native/bloodborne-recomp@8f31ec7c41f252730c6325d52647046baef7549f`; actual offsets and full 840-byte x64 structure, RcApi v4 and 40-byte RcFunction. Its self-contained AOT `native_aot_entry_v194` EXE links C functions directly and starts without any guest EBOOT, but deliberately uses **synthetic** logic. [Verified Win64+Linux CI](https://github.com/ProhorovIlja/bloodborne_pc_windows_port/actions/runs/41251184886). A no-EBOOT synthetic host is an architectural gate, **not a finished game**.
- **Native V195** `patch_upstream_win32_clock_v195.py`: a source-locked change of the *actual* upstream `src/recomp/rc.h` to use Win32 `QueryPerformanceCounter` for RDTSC instead of POSIX `clock_gettime` on Windows; preserves the original Linux and ARM paths. We build and execute C against the **original** upstream `rc.h` on native Windows and Ubuntu with an intentionally empty test-only Zydis header (real full-generator compilation MUST use actual Zydis). [Verified Win64+Linux CI](https://github.com/ProhorovIlja/bloodborne_pc_windows_port/actions/runs/41251411792). Does **not** claim game code or full generated library compiles yet.

## Upstream findings relevant DIRECTLY to independent Windows-native game code

| Upstream | Useful source | Important limitation |
|---|---|---|
| [bloodborne-native/bloodborne-recomp](https://github.com/bloodborne-native/bloodborne-recomp) | Huge **full-game** C AOT generator, x86 CPU state, functions/CFG, runtime helpers and native code architecture; docs report 240,978 of 241,821 functions recompiled | Upstream build is macOS ARM64; generated functions still invoke callbacks into a PS4-specific runtime and can fall back to interpretation; only 933 functions have independent call-by-call checks. Use for Win64 full game-code reconstruction, not keep PS4 ABI forever |
| [Astrr00/BloodbornePC](https://github.com/Astrr00/BloodbornePC) | C++ static recompilation for Windows, game-engine imports, actual rendering/audio/save progress | Describes ≈60% estimated progress and requires `bbgame.exe <eboot.bin>` **at runtime**; version 1.00 gameplay is more advanced than the user's 1.09. Needs major rework for strict EBOOT-free launch |
| [deadinside28/bloodborne_pc](https://github.com/deadinside28/bloodborne_pc), [Supermedo/bloodborne_pc](https://github.com/Supermedo/bloodborne_pc), bbhost, Awaken | Win32/Vulkan features, game-memory knowledge, fixes, input, frame timing, GPU/shader semantics, mods | Original PS4 EBOOT is still executed as native x86 code via compatibility services. This is not a model to preserve as the final runtime |
| Dark Souls III Windows (user-private files) | Related engine resource formats, PC graphics / input / save conventions and behavioral comparisons | It cannot be assumed identical to Bloodborne's 1.09 engine or used to reproduce an original proprietary binary/source. Treat as evidence and a reference, not an automatic engine replacement |
| shadPS4 and PS4-focused forks | Decode original GPU/IO semantics and bugs; borrow portable Vulkan or data conversion algorithms when licenses permit | Emulator runtime and PS4 kernel are **not** part of the final executable |

## Native-only engineering priorities (strict order)

1. **Broaden real-game AOT from ten tiny grammars to the FULL upstream recompiler's generated output.** Source-pin tools, use exact 1.09 private game for offline generation, port generator/lib build from Mac/ARM64 to Win64 LLVM/COFF, preserve original code hashes, guest entry/RET/call/flags/AVX/TLS/threads and all imports. Validate same-code Windows native output against the real original x86 instruction sequence privately. No public game-derived C or binaries.
2. Build a **self-contained Win64 code image** linked against our own platform/engine contracts. Remove EBOOT from startup dependencies, then remove all remaining guest ABI/Orbis handlers instead of only renaming an emulator.
3. Replace unresolved gameplay/engine imports with native code, support Bloodborne + DLC + chalice data, renderer and save pipeline, make a reproducible **first real game window/clinic** smoke and iterate through the game, not another isolated leaf-function counter.
4. Improve Windows native performance, input, graphics, crash safety, launcher and mods with measured real game benchmarks. Relevant upstream forks are donors for engineering concepts/code only if compatible and license-safe.
5. After full offline native gameplay: native multiplayer/server and all enhancements. YT 1.3.1/server-only feature patches are **not on the critical path to the core source-port**, and should not consume native-port engineering time.

No Fornex deployment, PR merge or public game file publication. Native work remains Draft until a genuine, complete Windows game exists. The end result cannot be claimed faster or more memory-efficient without comparisons on equal hardware; removing console translation *enables* improvements but does not guarantee them.
