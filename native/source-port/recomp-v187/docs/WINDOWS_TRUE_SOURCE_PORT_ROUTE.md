# Bloodborne V187+ true Windows source-port migration: actual upstream recompilation path

**Do not call native CPU execution of a PS4 ELF a rebuilt Windows game.** The target is a Windows executable using an independently compiled game core, native services, native engine graphics and the user's original data assets, with no PS4 ELF or a PS4-derived flat image loaded **at run time**.

## New key upstream, source-verified 2026-10-31

[**bloodborne-native/bloodborne-recomp**](https://github.com/bloodborne-native/bloodborne-recomp) commit `8f31ec7c41f252730c6325d52647046baef7549f`; `README.md`, `docs/RECOMPILATION.md`, `src/recomp/rc.h`, `tools/recomp/build_library.py`.

Its compiler takes the player's **own** original Bloodborne executable, scans the functions and outputs C code that LLVM builds into a native `librecomp.dylib` on **macOS ARM64**. The built game code stays private on the player's machine. Its documented progress is **240,978 / 241,821 functions executed through the generated library**; 10,861,735 / 11,268,132 instructions covered (96.4%); **99.1% is of the covered instructions** implemented directly as C; **933 / 241,821 functions** compared against recorded calls (they use additional per-instruction fuzzing). It still falls back to a translator/interpreter for import stubs, `setjmp` and patched functions.

This is neither Paleblood's independently restored readable C++, nor already a native Windows game. It is a **machine-generated source-based route** that could avoid hand-rewriting each of the game's ~150k-240k functions, depending on counting methods. The arithmetic and control-flow code is potentially portable; the surrounding platform/game services are not automatically portable.

**Direct present blockers** from `build_library.py`:
- `CFLAGS` hardcoded `--target=arm64-apple-macos15`, `-nostdinc`, app-specific shim headers.
- compiler distribution `bin/clang` and `bin/ld64.lld`, linking a **Mach-O .dylib** with Apple libSystem symbol rules;
- generated callback API `BB_RECOMP_API_VERSION=4` and `bb_recomp_init` currently loaded via macOS runtime `BB_RECOMP_LIB`;
- autogenerated CPU state includes guest register/memory sequencing, vector and atomic semantics, `setjmp` and runtime exceptions, not interchangeable with calling normal Win64 game methods;
- even the macOS generated library still runs in `bloodborne-runtime`, whose PS4 API/graphics support is present and required.

### Execution sequence, with explicit gates

1. **V187 (this PR):** test *exact* public `RcApi`, `RcFunction` and `RcInit` layout on both Windows x64 and Linux. A Windows **DLL from synthetic generated-like code** must load and callback correctly, with a negative incompatible-module test. The pinned upstream ABI verifier must fail on source drift. This establishes **a Windows PE module interface only**, not a Bloodborne function.
2. **Native Win64 code-generation backend:** support `x86_64-pc-windows-msvc` / Windows LLVM codegen and COFF `.obj`, export `bb_recomp_init`, build DLL with `lld-link`, use correct compiler builtins, exception/TLS model, x86 memory ordering and link diagnostics. Adapt source generator and build script without publishing the generated code. Compare **compiled outputs** against the upstream behavior on generated/offline tests. No `ld64.lld` nor Apple-only `--target`.
3. **Real user-game *private* recompilation:** generate source from the user's verified Bloodborne 1.09 (known clean SHA) **locally**, build a Win64 DLL, record a private digest/build manifest only, and run differential tests on a small chosen set of game functions. Never upload generated C/objects/DLL, original game bytes, traces or identifying data to GitHub/CI.
4. **Independently native runtime:** strip PS4 guest ELFs, PS4 libc/Kernel/HLE entrypoints and hardware kernel guest assumptions from the final launch path. Replace file VFS, memory/threading, timer, input, audio, save, physics/middleware integration with Win32 or cross-platform native library backends. A PS4 ELF at *installation/build time* is a legitimate input; **at gameplay runtime** no guest executable must be loaded/executed. This is the strict user requirement.
5. **Engine-level graphics, not GNM PM4:** compare [bbhost](https://github.com/droogie/bbhost) `docs/rendering.md`, [LanternEngine](https://github.com/Awakenchan/LanternEngine) `engine/docs/EMULATION_REMOVAL_PLAN.md`, and [bloodborne-runtime](https://github.com/bloodborne-native/bloodborne-runtime) `docs/NATIVE_RENDERER.md`. Reuse the documented GX/CoreGraphics2 draw-state boundary and DS3's equivalent **PC DX11 GX layer** as a design reference. Count remaining guest GPU instructions/waits; no GCN guest command processor in the final product. Original asset formats and shader data may need a legal build-time conversion.
6. **Gameplay integration:** verified original engine behavior (bosses, DLC, events, animation, save/loading), performance/leaks, then Yharnam Together's five-seat net protocol + server-authoritative control and authenticated direct P2P only for allowed high-frequency traffic. Live WAN/NAT, real two/then five-machine game sessions and >=99% measured 200-player delivery required.

#### Acceptance evidence: be exact

The **V186 native DCX/BND4 core** in PR #77 and **V187 Windows recompiled-module ABI** here are separate native building blocks that make *no* call to PS4 APIs or load a game ELF. This is valid native software progress, but neither contains Bloodborne gameplay. **No checked repository currently demonstrates the user's complete requested Windows-native, PS4-runtime-free Bloodborne game with five-player online.** A genuine code-recompiled Windows game module and an independently native engine/runtime are the next two hard gates.
